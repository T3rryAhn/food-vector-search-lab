# 결정 001: 실서비스 트랙은 같은 Lab 안에서 실행 코드와 분리한다

날짜: 2026-11-16 / 상태: 기록 구조 채택, 실행 코드 통합은 보류

## 배경

사용자는 서비스를 직접 사용하면서 식재료·낱개 식품이 메뉴로 추천되는 문제를 발견했다. 이후 평가에서 검색 조건 위반과 음식명 검색 실패도 재현됐다. 이 과정을 기술적 판단의 근거로 남기고 싶지만, 기존 Lab과 서비스의 코드/파일 구조가 다르다는 우려를 제기했다.

## 검토한 선택

- 기존 src에 곧바로 합치기: 공통 개념은 많지만 CLI/API, 메타 형식, 전처리, 의존성 차이가 숨겨지고 이전 실험의 재현성을 해친다. 기각.
- 별도 Lab 저장소 생성: 실행 프로젝트로 독립할 때 유용하지만 현재는 기존 연구와 운영 피드백의 연결이 끊기고 문서가 중복된다. 지금은 보류.
- 같은 저장소에 독립된 service-retrieval 트랙: 과거 연구와 이어서 읽을 수 있고 코드가 동일하다는 인상을 피할 수 있다. 채택.

## 결정과 조건

기존 src/requirements/과거 결과는 유지한다. 새 디렉터리는 평가 자료와 의사결정만 담는다. 이후 실행 비교 도구는 명시적 adapter 또는 버전 고정 서비스 snapshot으로 만든다. 운영 환경은 별도로 유지한다. 공통 엔진이 정말 필요해질 때만 추출하고 두 경로의 동등성 테스트를 먼저 만든다.

## 과거 판단의 재검토

기존 README의 'hard filter보다 soft guardrail'은 당시 후보 소실 문제에서 얻은 판단이다. 이번 한 끼 선택 화면에서는 노른자·소스가 결과에 남는 것도 실패다. 따라서 모든 속성에 일률적으로 감점을 적용하지 않고, **제품상 자격 조건(완성 메뉴 여부)과 취향 선호를 분리**하는 방향을 검증한다. 아직 필터 개선 효과를 측정한 것은 아니다.

## 별도 저장소로 분리할 시점

독립 패키지/릴리스 주기 또는 협업자가 생기거나, API/프론트/배포 코드가 실험 기록보다 커질 때 다시 판단한다. 그때도 이 트랙의 run과 결정 기록은 추적 가능하게 연결한다.
